# Фабрика: як запустити й адаптувати під ваші вимоги

Бонус WS9 (+10, необов'язково). Що здати — у [README](../README.md#бонус-10-фабрика-в-двійнику); двійник з окремим
розгортанням — у [twin-deploy](twin-deploy.md). Промпти — [F07–F13, F15, F18](prompts.md#бонус-фабрика-в-двійнику);
приклади й шаблон звіту — [`materials/factory/`](../materials/factory/README.md).

Курс-редакція фабрики називає двійник «близнюком» — це те саме: окрема копія вашого проєкту зі своїм репо, базою й
хостингом.

## Навіщо в роботі

У WS6–WS8 ви самі вели зміну від вимоги до проду: спека, тести, код, ворота CI, UAT, пакет доказів. Кожен крок
запускала людина й сама вирішувала, чи «досить». Фабрика — той самий процес, але його виконує лінія з фіксованим
порядком кроків, і вона сама каже «ні», якщо доказу бракує. Бонус дає вам **власні цифри**: той самий зріз 3 ви
робите звичайно в основному репо, а фабрика — паралельно в двійнику, і ви чесно порівнюєте час, гроші, втручання й
вади.

**Фабрика в п'яти рядках:**

1. **Задача** — JSON із вимогами PM (ID вимоги = AC ID) і тим, чим кожну доводити; людина схвалює її **намір**.
2. **Допуск** — фабрика ще до агента відмовляє задачі, яку не можна перевірити (немає червоного тесту, «TBD» у
   нефункціональних вимогах).
3. **Будівельник** — Claude Code без людини пише код в одноразовій копії репо; хук політики не пускає його до тестів,
   секретів і чужих тек.
4. **Ворота** — від дешевих до дорогих: цілісність тестів, розмір diff, супроводжуваність, видимі тести, повтор,
   мутації, приховані сценарії, рев'ю іншою моделлю; будь-що, крім `PASS`, зупиняє зміну.
5. **Пакет доказів** — «вимога → доказ», ворота, «Не перевірено», вартість; у двійнику він стає описом PR, який
   зливається сам після обов'язкових перевірок CI.

Аналогія з заняття: не «майстер-одинак», що сам робить і сам себе перевіряє, а цех із відділом технічного
контролю.

## Що таке фабрика курсу: першоджерело і курс-редакція

  принципами (23 виконуються кодом, 12 — частково). Вона зупиняється на **локальній гілці** `factory/<run-id>`:
  нічого не пушить і не зливає.
- **Курс-редакція** — [`koldovsky/2026-quitcode-09-factory`](https://github.com/koldovsky/2026-quitcode-09-factory):
  те саме ядро плюс профіль Next.js + Vitest (`next-vitest`), адаптер тестів `factory-tap.mjs`, імпортер вимог PM
  `tools/ac-to-task.mjs`, команди `deliver` (push → PR з пакетом доказів → автозлиття) і `uat` (UAT після деплою),
  українські інструкції в `docs/uk/`. Для бонусу беріть **курс-редакцію**.

### Що потрібно

- Node 22.17+ (перевірено на 24), git, [GitHub CLI](https://cli.github.com/) з `gh auth login`.
- **Claude Code як нативний файл** (`claude.exe`, зазвичай `%USERPROFILE%\.local\bin\claude.exe`) і вхід у нього.
  `claude`, встановлений через npm, фабрика запустити не може (це shell-обгортка). Cursor — [нижче](#якщо-у-вас-cursor-а-не-claude-code).
- Двійник з власним Supabase і Vercel — [twin-deploy](twin-deploy.md). **Ніколи** не спрямовуйте фабрику на основне репо.

### Три місця — три власники

| Місце | Приклад шляху | Що там | Хто пише |
|---|---|---|---|
| **контроль** (control) | `C:\pf\control` | `factory.json`, AI-політика, правила, задачі, приховані сценарії | ви; фабрика лише читає |
| **ціль** (target) | `C:\pf\twin` | робоча копія **двійника** | фабрика додає гілку `factory/<run-id>` |
| **склад** (store) | `C:\pf\store` | прогони, журнал подій, сліди, схвалення, пакети доказів | лише фабрика |

**Контроль — завжди поза репо двійника.** Будівельник працює в копії двійника; якби задачі й приховані сценарії
лежали там, він міг би їх прочитати («підглянути відповіді»). Короткі шляхи `C:\pf\…` рятують від обмеження Windows у
260 символів.

### Встановити

```powershell
git clone https://github.com/koldovsky/2026-quitcode-09-factory C:\pf\factory
cd C:\pf\factory; npm ci
Copy-Item -Recurse C:\pf\factory\examples\next-supabase\control C:\pf\control
```

Позначення на сесію PowerShell (тоді `--control`, `--target`, `--store` писати не треба):

```powershell
$env:FACTORY_CONTROL = "C:\pf\control"
$env:FACTORY_TARGET  = "C:\pf\twin"
$env:FACTORY_STORE   = "C:\pf\store"
function F { node C:\pf\factory\bin\factory.mjs @args }
```

У `C:\pf\control` відредагуйте:

- `knowledge/conventions.md` — ключове з `AGENTS.md` вашого проєкту (будівельник не читає `CLAUDE.md` і навички репо
  — це не перевірено, тож домовленості пишемо сюди);
- `rules.json` — правила залежностей для ваших тек `src/**`;
- `factory.json`, розділ `delivery` — допишіть `"uatUrl": "https://<двійник>.vercel.app"`.

Що означає кожен файл — `C:\pf\control\README.md`. Модель у прикладі — Sonnet і будівельником, і рев'юером; бюджети
`runUsd 8` (стеля на прогін), `dailyUsd 30` (стеля на день), 3 спроби.

## Запуск без ключа API

Те, що показано на занятті: чотири сценарні будівельники (чесний, «підганяє під тести», «псує тести», «підглядає»)
проходять ту саму лінію воріт. Ключ API і Claude Code не потрібні.

```powershell
cd C:\pf\factory
npm test
npm run demo
node bin/factory.mjs conformance
```

- `npm run demo` — код виходу 0; шість кроків `=== 1.` … `=== 6.`; підгонка падає на прихованих сценаріях
  (`FAIL holdouts`), підробка тестів — на `FAIL integrity`, підглядання відхиляє хук (`denied Read: path outside the
  workspace`).
- `conformance` — 35 принципів: 23 виконуються кодом, 12 — частково.

Вивід дайте агенту з промптом [F07](prompts.md#f07): він пояснить таблицею, які ворота що зловили. Вартість у виводі
демо **задекларована сценарними будівельниками** — це не справжня ціна.

## Червоні тести в двійнику

**Навіщо.** Фабрика доводить зміну тестом, який **падає до неї й проходить після** (fail-to-pass). Допуск відхилить
задачу, якщо тесту з ID критерію немає, а базовий прогін — якщо тест уже зелений («already passes»).

**Де.** У двійнику, на **локальній** гілці `tests-first` від тегу `ws9-base`. `main` двійника червоних тестів тримати не
може: required check `app` впаде. Гілка дійде в `main` одним PR разом із кодом фабрики: фабрика будує свою гілку
поверх `tests-first`.

```powershell
cd C:\pf\twin
git switch -c tests-first ws9-base
Copy-Item C:\pf\factory\templates\next-vitest\factory-tap.mjs scripts\factory-tap.mjs
node scripts/factory-tap.mjs --checks   # TAP: typecheck, lint, ac-coverage і рядок на кожен AC — усе «ok»
```

**`factory-tap.mjs`** — адаптер: проганяє Vitest і друкує стабільний TAP (рядок «ok / not ok» на кожен AC ID). Саме
ці рядки фабрика читає як `visible:<AC ID>`. Якщо в проєкті є fallow (шаблон курсу), допишіть
`"scripts/factory-tap.mjs"` у `entry` файлу `.fallowrc.jsonc` — скрипт запускають руками, і без цього fallow позначить
його «unused file» (саме так сталося на демо-двійнику).

**Тести пише окрема сесія Claude Code** за промптом [F18](prompts.md#f18) (правила F02 + доповнення): з тексту AC, а не з
основного репо; кожен AC — у новому файлі; назва кожного тесту починається з AC ID (`it("AC-X-01: …")`).

| Рівень | Що бачить фабрика |
|---|---|
| Vitest (домен), PGlite (правила бази) | так — це `visible:<AC>` |
| Playwright `tests/e2e/*.spec.ts` з тегом `@uat` | ні — це UAT після деплою ([F03](prompts.md#f03)) |

AC, що видно лише в браузері (стан сторінки після дії), фабрика довести не може: його доводить UAT на проді
двійника. Специфікацію Playwright для нього пишіть у тому самому коміті — вона піде в PR фабрики й запуститься в CI.

```powershell
git add -A; git commit -m "Тести спершу: AC-X-01, AC-X-02, AC-X-03"
node scripts/factory-tap.mjs            # рядки AC-X-01… — «not ok», усе інше — «ok»
```

Не пуште й не зливайте `tests-first` окремо. **Перевірка:** `git diff ws9-base --stat` — лише нові файли тестів,
`factory-tap.mjs` і рядки `docs/conformance.md` без шляхів `src/…`.

## Імпортер під формат PM

**Що робить.** `tools/ac-to-task.mjs` перетворює вимогу PM на задачу фабрики так, що **ID критерію PM = ID вимоги в
задачі = назва рядка TAP**. Тоді ланцюжок «AC → тест → зміна → доказ» не рветься, і PM бачить у пакеті доказів ті самі
`AC-…`, що й у своїй вимозі. Це **єдина зміна коду фабрики**, яку ви робите.

### Крок 1. Який формат у вашого PM

| Де PM веде вимоги | Як записано AC | Прапорці імпортера |
|---|---|---|
| `docs/requirements/<NN>-<slug>.md` у репо PM (після `/requirements-sync` — `requirements/` у двійнику) | один рядок: `- AC-X-01: Дано … Коли … Тоді …` | `--file <файл>` (типово `--format lines`) |
| issue «Вимога» з міткою `requirement` | чекбокси: `- [ ] **AC-X-01** — Дано …` | `--issue <pm>/<team-slug>-spec#12` (потрібен `gh` з доступом до репо PM) |
| будь-де | таблиця `\| ID \| Дано \| Коли \| Тоді \|` | `--format table` |
| будь-де | блок `### AC-X-01 …` і рядки `**Дано**` / `**Коли**` / `**Тоді**` | `--format block` |

Подивіться **справжню** вимогу зрізу 3 вашого PM і знайдіть рядок таблиці. Збігається — адаптувати нічого не треба,
лише запустіть. Не збігається (інший вигляд ID, Gherkin, експорт Jira, AC у коментарях) — адаптуйте за
`C:\pf\factory\docs\uk\adapt-importer.md`: шість позначених місць «ТОЧКА РОЗШИРЕННЯ 1…6». Якщо змінюєте вигляд ID —
той самий вираз змініть у `scripts/factory-tap.mjs` двійника (`AC` і `AC_IN_SOURCE`).

### Крок 2. Адаптація — промпт F09

Дайте агенту [F09](prompts.md#f09) у **копії курс-редакції** `C:\pf\factory`. Зміни — лише імпортер (або адаптер поруч)
і його тест; ворота, хук політики, оцінювачі й захищені файли фабрики не змінюйте.

**Де лежить адаптер.** F09 називає теку `control/tools/`. У курс-редакції імпортер працює лише з теки фабрики:
`tools/ac-to-task.mjs` імпортує `../src/util.mjs`, і копія в `C:\pf\control\tools\` падає з `ERR_MODULE_NOT_FOUND`
(перевірено). Тому:

- адаптер — у `C:\pf\factory\tools\` (свій формат — новий файл `tools/<team-slug>-to-task.mjs` поруч або зміни в
  точках розширення), тест — у `tests/ws9.test.mjs` з фікстурою в `tests/fixtures/ws9/`;
- закомітьте у **свій fork** курс-редакції (`<dev>/2026-quitcode-09-factory`, гілка `team/<team-slug>`) і дайте
  посилання на коміт у полі «Фабрика й імпортер» файлу здачі. Задачі (`tasks/*.json`) лишаються в теці контролю.

### Крок 3. Запуск

```powershell
node C:\pf\factory\tools\ac-to-task.mjs --file C:\pf\twin\requirements\03-x.md `
  --ac AC-X-01,AC-X-02,AC-X-03 --id x-db --holdout x-db --target C:\pf\twin --size medium `
  --out C:\pf\control\tasks\x-db.json
```

- `--out`, а не `>`: у Windows PowerShell 5.1 `>` пише UTF-16, і фабрика такий файл не прочитає.
- `--target` додає pass-to-pass: AC, уже «реалізовано» в `docs/conformance.md` двійника, з тестом Vitest (захист від
  регресії). AC лише з e2e дає попередження, а не pass-to-pass.
- **Розмір.** Більше двох вимог → `size: medium` → після схвалення наміру фабрика спершу просить план, і людина його
  схвалює (`F approve plan`). Якщо `size` не задати, фабрика рахує сама: ≤ 2 — `small`, 3–5 — `medium`. **Чесно про
  демо:** там задали `--size small` для трьох AC (одна функція бази й одна сторінка), тож етапу плану не було. Для
  бонусу йдіть за F09 і F11: `medium` і `approve plan`.
- Одна задача — 1–3 AC. Великий зріз діліть на кілька задач (наприклад, «правила бази» і «сторінка»).

### Крок 4. Дві речі руками в JSON задачі

1. **П'ять `nonFunctionals`** — `security`, `accessRules`, `idempotency`, `tenancy`, `failureModes`. Імпортер пише
   `TBD` навмисно: «TBD = не готово». Заповнюйте разом із PM. **Де саме фабрика відмовить:** `F approve intent` задачу
   з `TBD` **приймає**, а відмовляє `F run` на допуску — ще до агента, за $0:

   ```text
   run-…  x-db  state=refused  (task not admissible)
     - non-functional "security" is still undecided
     …
     attempts 0/? · cost $0.0000
   ```

2. **Контракт в `intent`**, який фіксують ваші червоні тести: назви нових функцій бази чи модулів, шляхи файлів,
   дослівні повідомлення з вимоги, `data-testid`. Імпортер дає лише «навіщо» і джерело. Зразок заповненої задачі з
   демо — [`materials/factory/bulk-db.example.json`](../materials/factory/bulk-db.example.json).

**Перевірка:** кількість AC на вході = кількість `requirements[]`; ID збігаються символ у символ; `description` —
дослівно «Дано / Коли / Тоді»; у `verifiedBy` лише `visible:…` і `holdout:…`. Після коміту тестів (крок 4 таблиці)
запустіть імпорт ще раз **без `--out`** (інакше він перезапише заповнені `nonFunctionals`): попередження «не мають
Vitest-тесту» мають зникнути.

## Приховані сценарії з AC

**Що це.** Приховані сценарії (holdouts) — «контрольна з невідомими задачами»: тести Vitest/PGlite, які пише людина з
тексту AC і яких будівельник не бачить. Він дізнається лише число («3/3»). Ловлять підгонку під видимі тести: код, що
проходить лише вивчені приклади, тут падає.

**Хто й де.** Окрема сесія ([F10](prompts.md#f10)) у теці контролю, не в робочій копії двійника; або PM / QA в AI-чаті
без доступу до коду. Формат — `C:\pf\control\holdouts\example.json` (поля `id`, `ac`, `input` ≥ 6 символів для
перевірки на витік, `source` з тестом; назви тестів починаються з `<id>:`). Збережіть як
`C:\pf\control\holdouts\x-db.json` — назва набору = `--holdout` імпортера.

**Скільки.** За F10 — на кожен AC щонайменше три: звичайний, межа, відмова. Очікування — з «Тоді», не з коду. **Чесно
про демо:** там було 3 сценарії на 3 AC (по одному); для бонусу йдіть за F10.

**Печатка.** Запечатаний набір — зашифрований файл `x-db.json.enc` (AES-256-GCM); відкритий файл видаляється.

```powershell
$env:FACTORY_HOLDOUT_KEY = "<щонайменше 16 символів>"   # лише у вашому терміналі
F holdouts seal x-db
```

Ключ — у менеджер паролів. Не пишіть його у файли, у чат агенту чи в задачу; без нього в тій самій сесії PowerShell
прогін зупиниться. Файл здачі зі значенням ключа CodeRabbit позначить ❌.

## Прогін і пакет доказів

```powershell
F run x-db --as <ваш-логін>
F status
F proof <run-id>
```

Фабрика веде прогін сама: допуск → (план) → будівельник → ворота → рев'ю → рівень автономії → випуск у **локальну**
гілку `factory/<run-id>`. Червоні ворота дають нову спробу; бюджет — `maxAttempts 3`, `runUsd 8`.

**Що ви побачите (демо-двійник, 02.11.2026, задача на AC-BULK-01…03):**

```text
run-20261102105148-3f6cd9  bulk-db  state=released
  attempts 1/3 · cost $0.3500
  PASS       boundary         29 tool call(s) decided by the policy hook, 2 denied
  PASS       integrity        287 protected file(s) unchanged
  PASS       diff             7 file(s), 115 changed lines
  PASS       maintainability  Maintainability passed: no findings in 5 checked files (…)
  PASS       visible-tests    102 visible test(s) passed
  PASS       repeat           outcomes identical across 2 runs
  PASS       holdouts         3/3 hidden scenario(s) passed
  PASS       review           reviewer could not refute the change (0 non-blocking note(s), …)
  n/a        mutation: no mutable operators on the changed lines
  released to branch factory/run-20261102105148-3f6cd9 at 41ce8a63f8a3 · … · not pushed
```

160 с, $0.35 (будівельник Sonnet $0.26, рев'юер Sonnet $0.09), перша спроба з трьох. **Mutation — n/a, а не PASS:**
головна логіка «все або нічого» жила в SQL-міграції, а мутації SQL не дивляться; у змінених рядках `src/**` не було
операторів, які можна змінити. Сили тестів ці ворота тут **не довели**.

### Як читати пакет доказів — F12

`F proof <run-id>` друкує пакет і його дайджест. Читайте з промптом [F12](prompts.md#f12), у такому порядку:

1. **«Not verified»** — що НЕ перевірено (на демо: ізоляція лише на рівні політики в одному обліковому записі ОС;
   mutation — not applicable). Кожен пункт: чим загрожує на проді.
2. **«Requirements and evidence»** — для кожного AC: видимий тест ✓ і приховані сценарії; чи досить цього для «Тоді».
3. **«Gates»** — жодного `NOT-EARNED`; «not applicable» не видається за перевірку.
4. **«Change»** — які файли змінено. На демо будівельник сам позначив рядки `docs/conformance.md` «реалізовано» (так
   просив `intent`): це «автор перевіряє себе» — рядки перевіряєте ви.
5. **«Cost and provenance»** — вартість з усіма спробами, моделі, базовий коміт.

Дайджест і run id — у файл здачі.

## Коли прогін зупинився

| Стан | Що означає | Що робите ви |
|---|---|---|
| `refused` (task not admissible) | допуск відмовив до агента, $0 | читаєте причини: `TBD`, тест не існує чи вже зелений, немає свіжого `doctor`; виправляєте задачу чи тести, схвалюєте намір знову |
| `awaiting-plan-approval` | задача `medium`, план готовий | читаєте `plan.md`, `F approve plan` |
| `needs-human` | спроби вичерпано; фабрика питає «What should change — the task, the acceptance cases, or the approach?» | розбираєте з [F13](prompts.md#f13), рішення — ваше |
| прогін перервано (Ctrl+C, сон ноутбука) | процес зупинився посеред стадії | `F resume <run-id> --recover` або новий `F run` |

Рішення на `needs-human`:

- **змінити підхід** — підказка будівельнику без відповідей прихованих сценаріїв:
  `F answer <run-id> --as <логін> --text "<підказка>"` (дає ще одну спробу);
- **змінити задачу** (намір чи вимоги) — правите JSON, `F approve intent` знову, новий `F run`;
- **змінити приймальні сценарії** — лише якщо вони суперечать AC, і тоді це питання до PM;
- **закрити** — `F sweep` закриває прогони, на які ніхто не відповів до строку ескалації, дією за замовчуванням.

Захищені тести, ворота й оцінювачі **не послаблюйте** — за це бонус не зараховується. Аварійна зупинка всіх агентів —
`F stop --as <логін>`, зняти — `F start --as <логін>`. Кожен `answer`, `resume`, схвалення й ручний коміт — втручання
для звіту.

## Автозлиття, деплой двійника і UAT на кожен AC

### Поставка

```powershell
F deliver <run-id>
```

`deliver` пушить гілку `factory/<run-id>`, відкриває PR з пакетом доказів в описі і вмикає автозлиття
(`gh pr merge --auto --squash`), бо рівень у двійнику — `auto` (`delivery.autoMerge: "auto-tier"` у `factory.json`).
GitHub зливає PR, коли пройдуть **обов'язкові** перевірки ruleset. Після злиття CI `db-deploy` застосовує нові
міграції до Supabase **двійника**, Vercel розгортає прод двійника.

Дві умови в репо двійника обов'язкові ([twin-deploy](twin-deploy.md#github-автозлиття-ruleset-environment-production)):
**Allow auto-merge** і **ruleset з required checks**. Без required checks GitHub не має чого чекати, і PR зливається
одразу, ще до CI. Дорадча перевірка (fallow) може бути червоною, а PR однаково зіллється.

**Чесно про демо.** Прогін на двійнику зроблено версією фабрики, у якій ще не було `deliver`, тож поставку виконали
вручну:

```powershell
git -C C:\pf\twin push -u origin factory/<run-id>
gh pr create --repo <dev>/<team-slug>-factory --base main --head factory/<run-id> `
  --title "<назва задачі> — фабрика <run-id>" --body-file C:\pf\store\runs\<run-id>\proof-pack.md
gh pr merge <N> --repo <dev>/<team-slug>-factory --auto --squash
```

`F deliver` і `F uat` у курс-редакції перевірено автотестами з фейковим `gh`, на живому репо — ще ні. Не спрацювало —
ці три команди і є План Б. Запускайте їх **самі** у своєму терміналі: агентам автозлиття й злиття PR зазвичай
заборонено дозволами, і це правильно.

На демо: [PR #3](https://github.com/koldovsky/2026-quitcode-09-leave-portal-factory/pull/3) двійника — обов'язкові
`spec`, `app`, `conformance`, `db-check` зелені, e2e у CI 11/11; дорадчий fallow червоний (складність `ManagePage` 22 —
від фабрики; «unused file» `scripts/factory-tap.mjs` — з людського коміту тестів-спершу); злито автоматично squash-ем,
`db-deploy` застосував міграцію.

### Перевірити деплой

- Actions двійника → CI на `main` → job `db-deploy`: у лозі є «Applying migration …». Без секрету `SUPABASE_DB_URL` job
  **мовчки пропускає** міграції і все одно зелений.
- `https://<двійник>.vercel.app/api/health` → `sha` = коміт злиття, `db: ok`.

### UAT на кожен AC

Той самий конвеєр WS8 ([F03](prompts.md#f03), [F04](prompts.md#f04)), лише URL — проду двійника:

```powershell
F uat <run-id> --url https://<двійник>.vercel.app --as <ваш-логін> --grep "AC-X"
```

`F uat` чекає злиття PR і поки `/api/health` покаже коміт злиття, тоді запускає `node scripts/uat/run.mjs --url …
--grep …` вашого двійника. Без `--grep` він бере лише AC задачі — а AC, що видно лише в браузері, у задачі немає.
Тому `--grep "AC-X"` (префікс усіх AC зрізу 3): так UAT пройде **кожен** AC. План Б — той самий рядок напряму:

```powershell
cd C:\pf\twin; git switch main; git pull
npm run uat -- --url https://<двійник>.vercel.app --grep "AC-X"
```

FAIL в UAT → `F uat` записує інцидент і понижує клас змін: наступна така зміна чекатиме людину. NEEDS-HUMAN —
відкрийте кадр і перевірте в браузері самі (на демо AC-BULK-01…03 — PASS, AC-BULK-04 — NEEDS-HUMAN: на кадрі не
поміщався блок «Вирішені»; рішення — за PM).

Звіт UAT (`docs/qa/uat/<дата>/`) з'являється в робочій копії двійника: закомітьте його в двійник **звичайним PR** (як у
WS8), інакше наступний `F doctor` скаже «дерево не чисте». Наступна задача: `git switch main; git pull`, нова гілка
тестів — і знову з червоних тестів.

## Якщо у вас Cursor, а не Claude Code

**Запускайте фабрику з Claude Code, навіть якщо щодня пишете в Cursor.** Фабрика викликає агента сама, у фоновому
режимі, тож ваша IDE на результат не впливає. Тести, вимоги, приховані сценарії й адаптацію імпортера можна робити в
Cursor; `F run` — з терміналу, де є нативний `claude.exe` і вхід у Claude Code.

Чому: лише для Claude Code фабрика має хук політики (кожен виклик інструмента вирішує фабрика), ворота boundary і облік
вартості з бюджетом. Загальний адаптер `command` для інших CLI **з Cursor не перевірено**: хука немає, інструменти
агента нічим не обмежені, вартість невідома, AI-політика мусить явно дозволити `allowUnconfinedAgent`. Подробиці —
`C:\pf\factory\docs\uk\cursor.md`. Якщо Claude Code недоступний — зробіть бонус частково (двійник, імпортер, червоні
тести, приховані сценарії, `doctor`) і чесно опишіть, де зупинилися.
